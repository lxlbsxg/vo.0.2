# Votely 网站规划 v0.1

> 用途：交给 Linux 端的编码会话作为建站依据。机制细节以《Votely 规则文档 v0.1》为准，本文件只描述网站要做什么。

## 0. 第一版范围（MVP）

- **积分模拟版，不涉及真钱**：所有"资金"用积分表示，用来验证规则能不能跑通、人们会不会按信誉投票。
- 真钱、银行卡绑定、股票发放、合规，全部留到之后的版本。
- 目标：能完整跑通一个 Chapter：发布 → 1st Roll → 决定性胜利 → cinnamon's Roll → Chapter 结束兑现。

## 1. 用户角色

| 角色 | 能做什么 |
| --- | --- |
| 企业 / 团队 | 建 profile、发布 Chapter、提前公布进度节点、上传审核文件、提出仓2价格 |
| cinnamons（散户） | 浏览、买入/退出/转卖信息值、查看持仓、参与监督 |
| 审核员（平台） | 审核企业身份和节点文件、确认节点是否达成 |

## 2. 页面

1. **首页**：正在进行的 Chapter 列表，按信息值、阶段（1st Roll / cinnamon's Roll）、行业筛选。
2. **Chapter 详情页**（核心页面）
   - 信息正文、资金用途说明
   - 当前阶段、信息值、人数、资金中位数
   - 进度节点时间线：已提前公布的全部节点，已验证的标记完成
   - 时间权重斜率图：当前进场能拿到的权重
   - 期限与剩余修改次数（最多 3 次）
   - 买入 / 退出 / 转卖按钮
3. **企业 profile**
   - 企业介绍、认证状态
   - **所有 Chapter 的成败记录（强制公开）**
   - 企业自选关联（标记）的 Chapter
4. **我的持仓**：每个 Chapter 的持有量、时间权重、当前价值、已分配的 20%、兑现记录。
5. **企业发布流程**
   - 填写信息 → 列出全部进度节点并标明哪个是"决定性胜利" → 设定期限 → 上传审核文件 → 提交审核
   - 任何影响市场走向的更新必须提前 24 小时排期发布
6. **审核后台**：待审企业、待审节点文件、通过/驳回。
7. **注册 / 账户**：一个人最多 5 个账户，账户归属同一个"人"，计算人数时只算 1。

## 3. 数据模型（初稿）

- **Person**：真实个人；拥有最多 5 个 Account
- **Account**：属于一个 Person；持有积分
- **Company**：认证状态、profile
- **Chapter**：属于 Company；阶段、期限、剩余修改次数、仓2价格、状态（进行中 / 仓一失败 / 仓二中 / 已结束）
- **Milestone**：属于 Chapter；描述、是否为决定性胜利、计划公布时间、验证状态、审核文件
- **Holding**：Account × Chapter；数量、买入时所处阶段（决定时间权重）
- **Trade**：买入 / 退出 / 转卖记录；转卖时买方继承卖方的时间权重
- **Announcement**：企业更新；发布时间必须 ≥ 创建时间 + 24 小时

## 4. 需要实现的规则（摘要）

- 1st Roll：资金托管，企业拿不到；可直接从托管退款；持仓可转卖
- 仓一成功 = 决定性胜利节点通过审核；期限到且 3 次修改用完仍未达成 = 失败，全额退回
- 仓2：企业提出价格并写明理由，不能低于仓1平均价；设认购期，未达最低认购额可下调重开
- 仓2买家每笔抽 20%：一部分分给仓1持有人（按时间权重，按已验证节点分批释放），一部分进企业
- 信息值取人数和资金中位数（组合方式待定，先做成可配置参数）
- 时间权重按斜率随节点下降（斜率算法待定，先做成可配置参数）
- Chapter 结束时兑现：股票 + 项目收益分成（模拟版里用积分表示）

## 5. 技术建议（可改）

- 前端 + 后端：Next.js（TypeScript）
- 数据库：SQLite 起步，之后换 PostgreSQL
- 规则逻辑单独放在一个模块里，方便以后调整参数和写测试
- 先做：注册 → 企业发布 Chapter → 买入 → 节点审核 → 仓一成功/失败 这条主线

## 6. 待定（会影响网站的）

- 信息值中人数与中位数怎么组合
- 斜率由市场决定的具体算法
- 散户监督权具体是什么（举报、投票、还是只看）
- 企业 profile 还需要展示什么
